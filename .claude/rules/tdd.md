# TDD Rule

> **이 규칙은 Rigid다 — 상황에 맞게 변형하지 마라.** 예외가 필요하다고 판단되면 규칙을 어기지 말고 사용자에게 먼저 확인하라.

## 0. 우선순위

이 파일은 **기본값(fallback)** 이다. 프로젝트 루트 또는 하위 디렉토리의 `CLAUDE.md`/`AGENTS.md`에 TDD 관련 규칙이 명시되어 있으면 **그쪽이 우선**한다. 충돌 시 이 파일의 해당 조항은 무시한다.

## 1. 적용 기준

### 반드시 TDD 적용

- **비즈니스 로직** (계산, 상태 전이, 도메인 규칙)
- **API 엔드포인트 / 서버 핸들러**
- **유틸리티 / 순수 함수**
- **버그 수정** (재현 테스트 없이 수정 금지)

### TDD 불필요

- **타입 정의** (interface, type alias)
- **설정 파일** (config, 빌드/린트 설정)
- **순수 UI 마크업** (로직 없는 프레젠테이셔널 컴포넌트)
- **SQL / 마이그레이션 스크립트**

경계가 모호하면(예: 로직이 섞인 컴포넌트) **적용 대상으로 간주**한다.

## 2. RED-GREEN-REFACTOR 사이클

### RED

- **하나의 동작(behavior) = 하나의 테스트**. 여러 동작을 한 테스트에 묶지 마라.
- 테스트 작성 후 **반드시 실행**해서 실패를 눈으로 확인한다. 실행하지 않고 넘어가는 것은 금지.
- 실패 이유는 반드시 **"기능 미구현"** 이어야 한다. 문법 오류, import 누락, 오타로 인한 실패는 RED가 아니다 — 고치고 다시 실행하라.

### GREEN

- 테스트를 통과시키는 **최소한의 코드만** 작성한다.
- **YAGNI**: 지금 테스트가 요구하지 않는 기능·분기·매개변수를 추가하지 마라.
- 통과 확인은 **신규 테스트 + 기존 테스트 전체**를 대상으로 한다. 신규 테스트만 통과하고 기존 테스트를 깨뜨리면 GREEN이 아니다.

### REFACTOR

- 중복 제거, 이름 개선, 헬퍼/함수 추출을 수행한다.
- 이 단계 내내 **테스트는 계속 green**이어야 한다. 리팩터링 중 테스트를 잠시 꺼두는 것은 금지.
- **새로운 동작을 추가하지 마라.** 새 동작이 필요하면 다음 사이클의 RED로 넘어가라.

### 반복

REFACTOR가 끝나면 다음 동작에 대한 **RED로 돌아간다.** 사이클을 건너뛰고 여러 동작을 한 번에 구현하지 마라.

## 3. 삭제 강제 규칙

- 테스트보다 프로덕션 코드를 먼저 작성한 사실을 발견하면, **그 코드를 삭제**하고 RED부터 다시 시작한다.
- "일단 참고용으로 남겨두기"도 금지한다. 주석 처리, 별도 파일 보관, `.bak` 등 어떤 형태로도 남기지 마라 — 완전히 삭제한다.

## 4. 변명 차단표

| 변명 | 반론 |
|---|---|
| "너무 단순해서 테스트 불필요" | 단순한 코드일수록 테스트 작성 비용도 낮다. 단순함은 생략의 근거가 아니라 작성이 쉬운 이유다. |
| "나중에 추가하겠다" | "나중"은 오지 않는다. 테스트 없는 코드는 기준선(baseline)이 되어 이후 회귀를 잡아내지 못한다. |
| "시간이 없다" | 테스트 없이 짠 코드는 디버깅 시간으로 그 차이를 반드시 되갚는다. 지금 쓰는 시간이 더 싸다. |
| "삭제하면 낭비" | 순서를 어기고 짠 코드는 검증되지 않은 코드다. 남겨두면 "동작할 것"이라는 근거 없는 확신만 남는다. |
| "프로토타입이다" | 프로토타입은 대개 그대로 프로덕션에 들어간다. 지금 규칙을 어기면 나중에 되돌릴 지점이 없다. |
