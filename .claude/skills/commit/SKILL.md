# commit: 변경사항 분석 후 컨벤션 커밋

현재 작업 디렉토리의 git 저장소에서 변경사항을 분석해 논리적 단위로 나누고, 각 단위마다 한국어 커밋 메시지를 작성해 사용자 승인 후 커밋한다.

## 워크플로우

### Step 1: 저장소 지침 확인

저장소 루트의 `AGENTS.md` 또는 `CLAUDE.md`에 커밋 메시지 컨벤션(포맷, 언어, 스코프 규칙 등)이 명시돼 있으면 그것을 우선 따른다. 없으면 이 스킬의 기본 규칙(아래 "커밋 메시지 규칙")을 사용한다.

`git log --oneline -20`으로 최근 커밋 스타일을 확인하고, 기존 컨벤션이 이 스킬의 기본 규칙과 다르면 기존 스타일에 맞춘다.

### Step 2: 변경사항 분석

- `git status`로 변경/추가/삭제된 파일 전체를 확인한다.
- `git diff`(스테이징 안 된 변경)와 `git diff --staged`(스테이징된 변경)로 실제 변경 내용을 확인한다.
- 시크릿이 포함될 수 있는 파일(`.env`, `credentials.*`, `*.pem`, `*.key` 등)이 변경 목록에 있으면 내용을 먼저 확인하고, 시크릿으로 보이면 사용자에게 알리고 해당 파일은 커밋 대상에서 제외할지 확인한다.

### Step 3: 논리적 단위로 분류

전체 변경사항을 하나의 커밋으로 뭉치지 않고, 목적이 다른 변경은 별도 커밋으로 나눈다. 분류 기준:

- **기능 단위**: 서로 다른 기능/모듈에 대한 변경은 분리한다.
- **성격 단위**: 기능 추가(`feat`), 버그 수정(`fix`), 리팩터링(`refactor`), 잡무(`chore`), 문서(`docs`), 테스트(`test`), 스타일(`style`) 등 성격이 다르면 분리한다.
- **의존 관계**: 한 변경이 다른 변경 없이는 의미가 없거나 빌드가 깨지는 경우에만 같은 커밋으로 묶는다.
- 변경이 하나의 논리적 단위로만 이루어져 있으면 굳이 쪼개지 않는다.

### Step 4: 커밋 메시지 작성

각 논리 단위마다 다음 형식으로 한국어 커밋 메시지를 작성한다.

```
<type>: <한국어 요약>

<필요 시 본문 — 무엇을·왜 변경했는지>
```

**커밋 메시지 규칙**

- `type`은 `feat`(기능 추가) / `fix`(버그 수정) / `refactor`(동작 변경 없는 구조 개선) / `chore`(빌드·설정·잡무) / `docs`(문서) / `test`(테스트) / `style`(포맷팅) 중 하나를 사용한다.
- 요약은 한국어로, 명령형 어미("~한다"보다는 "~추가", "~수정" 같은 간결한 명사형/동사형)로 50자 내외로 작성한다.
- 본문은 diff로 알 수 없는 "왜"가 있을 때만 추가한다. 코드만 봐도 알 수 있는 내용은 반복하지 않는다.
- 커밋 메시지 끝에 시스템에서 지시된 attribution(예: `Co-Authored-By`)이 있으면 반드시 포함한다.

### Step 5: 사용자 승인

커밋을 실행하기 전에 다음을 사용자에게 제시하고 승인을 받는다:

- 분류된 커밋 단위 목록 (각 단위에 포함될 파일과 커밋 메시지)
- 여러 단위로 나뉜 경우, 전체 계획을 먼저 보여준다.

사용자가 승인하면 각 단위를 `git add <해당 파일>`으로 스테이징한 뒤 `git commit -m`으로 커밋한다(`git add -A`/`git add .` 금지, 파일을 명시해서 추가한다). 사용자가 일부만 승인하거나 메시지 수정을 요청하면 그에 맞게 조정한다.

커밋 완료 후 `git status`로 결과를 확인해 보고한다. push는 사용자가 명시적으로 요청하지 않는 한 하지 않는다.
